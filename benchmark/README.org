#+TITLE: FatTable performance checks

* Transformations and rendering
  Run from the repository root:

  #+begin_src sh
    scripts/benchmark-formatting
    scripts/benchmark-formatting 10000
    BENCH_GROUP_SIZE=100 scripts/benchmark-formatting 1000
  #+end_src

  The optional positional argument is the row count (default: 4000).
  The wrapper can also be invoked by absolute path from another directory.

  The script warms each operation, then records three elapsed-time and
  allocated-object samples. Input construction and result hashing are outside
  the timed portion. The table shows median, minimum, and maximum times in
  milliseconds, plus median allocated-object counts.

  For raw JSON samples and full result digests, run:

  #+begin_src sh
    BENCH_ROWS=10000 bundle exec ruby -Ilib benchmark/transform_and_render.rb
  #+end_src

  Digests allow comparing the same workload across revisions on the same
  Ruby version. Compare medians;
  timings vary with hardware, Ruby, dependencies, and system load.

  This is a synthetic three-column workload, not a representative byr report.
  By default each input row is its own group for select/where, exercising
  group lookup heavily. Rendering uses an ungrouped table. BENCH_GROUP_SIZE
  changes the transformation workload; a value greater than BENCH_ROWS gives
  a single implicit group.

* Join baseline
  Run the separate join workload with a row count per input table:

  #+begin_src sh
    scripts/benchmark-joins
    scripts/benchmark-joins 100
    BENCH_ROWS=200 bundle exec ruby -Ilib benchmark/joins.rb
  #+end_src

  The join script defaults to 200 rows per input. The last command emits raw JSON
  samples and output digests. Both tables have two columns, duplicate keys
  (two rows per key), and approximately half their key ranges overlap.
  The benchmark covers natural inner, symbol-based inner, and natural full
  outer joins. It checks complete output rows and ordering against independently
  constructed expected results after warmup and every measured run.
  Setup, validation, output extraction, and hashing are outside timing;
  construction of the joined table is included.

  Baseline: Ruby 3.4.1, library revision =add96a3=, 2026-11-27. Three samples
  after warmup, medians below. Raw 200-row results are saved in
  =joins-baseline-200.jsonl= for later digest and allocation comparisons.

  | Operation     | 100 rows (ms) | 200 rows (ms) | 200-row allocations | Output rows (200) |
  |---------------+---------------+---------------+---------------------+-------------------|
  | natural_inner |        77.114 |       308.065 |             1629228 |               200 |
  | symbol_inner  |        75.238 |       299.941 |             1629232 |               200 |
  | natural_full  |        78.467 |       309.386 |             1685852 |               400 |

  Doubling both inputs approximately quadruples elapsed time in this workload.
  The baseline implementation compared every pair of rows. These synthetic
  results do not measure real byr joins.

** Indexed equality joins [2026-11-27 Fri]
   Natural and symbol-based equality joins now index right-hand rows by join
   keys, preserving their original order within each bucket. Arbitrary string
   conditions, cross joins, and unsupported key classes retain the evaluator
   path. Integer/decimal keys and Date/DateTime keys are normalized for hashing;
   candidate matches are still checked with Ruby's ==.

   Same 200-row workload and Ruby 3.4.1, three samples after warmup:

   | Operation     | Before (ms) | After (ms) | Speedup | Before allocations | After allocations |
   |---------------+-------------+------------+---------+--------------------+-------------------|
   | natural_inner |     308.065 |      2.801 |  110.0x |            1629228 |             30140 |
   | symbol_inner  |     299.941 |      2.807 |  106.9x |            1629232 |             30145 |
   | natural_full  |     309.386 |      7.938 |   39.0x |            1685852 |             86764 |

   All output digests match the saved baseline. Raw samples are in
   =joins-indexed-200.jsonl=. At 1,000 rows per input, median times were
   14.551 ms, 14.774 ms, and 40.178 ms respectively. These measurements show
   approximately linear growth for this workload; duplicate-heavy joins can
   still produce quadratic output. The index adds memory proportional to input
   rows and key width. Rational and other unusual Numeric keys fall back to
   the original path to preserve their comparison semantics.

* Prepared sort keys [2026-11-27 Fri]
  Run the sorting workload separately:

  #+begin_src sh
    scripts/benchmark-sort 4000
    BENCH_ROWS=4000 bundle exec ruby -Ilib benchmark/sort.rb
  #+end_src

  Uses a deterministic shuffle of five-column rows with repeated numeric keys,
  strings, dates, and boolean/nil keys. Measures complete table operations,
  including result construction and group boundaries. Expression sorting also
  includes evaluating the expression and creating its additional column.
  Input construction and output hashing are excluded. Each operation warms up
  once before three measured samples; figures below are medians on Ruby 3.4.1.

  | Operation       | Before (ms) | After (ms) | Speedup | Before allocations | After allocations |
  |-----------------+-------------+------------+---------+--------------------+-------------------|
  | numeric_sort    |     126.079 |    108.639 |   1.16x |            1311377 |           1170820 |
  | mixed_sort      |     167.943 |    116.713 |   1.44x |            1320598 |           1188567 |
  | expression_sort |     385.534 |    378.773 |   1.02x |            3909540 |           3766689 |

  Baseline library revision: =7ba2e42=. Raw results are saved in
  =sort-baseline-4000.jsonl= and =sort-prepared-4000.jsonl=. Digests of headers,
  complete rows, and group boundaries match for every operation. The small
  expression-sort timing difference may be normal run-to-run variation.

  Comparison keys and boolean normalization are now prepared once per row;
  grouping reuses the original unnormalized keys. This reduces temporary
  allocations during comparisons but retains key arrays for the duration of
  the sort, using memory proportional to rows times key count. Stable ties,
  mixed directions, and nil ordering are preserved. These are synthetic
  results, not measurements of a byr report.

* Initial measurements [2026-11-27 Fri]
  Local Ruby 3.4.1, 4,000 rows, three measured runs after warmup. Baseline
  measured before the optimizations branch edits. All result digests matched.

  | Operation              | Before (s) | After (s) | Speedup |
  |------------------------+------------+-----------+---------|
  | select with group expr |     0.2727 |    0.0733 |   3.72x |
  | where with group expr  |     0.2387 |    0.0427 |   5.59x |
  | text rendering         |     0.0979 |    0.0158 |   6.20x |

  Changes measured: a forward group cursor in select/where instead of a
  fresh boundary scan per row; appending report fragments to an owned mutable
  string instead of copying the accumulated output at every append.

  These figures illustrate the targeted workloads, not general application
  speedups. Profile actual byr reports before choosing subsequent changes.
